Efficient Code Lab

Understanding: Programs can be enhanced for efficiency. In this lab you will program a small board with a 5 by 5 light grid, two buttons and some sensors. You will design functions, respond to events, store data in variables, read sensors, and make code shorter, clearer and more reliable.

Learn

Eight short lessons in order. Each one has a model to try. Most models use the same practice board: a 5 by 5 grid of lights, button A, button B, and sensors for light and temperature. The board runs block code, the same kind of code you build in a visual block-based tool.

Lesson 1 · Designing a function
CS1.K1

You can design your own functions

In Science 7 you used built-in functions, like move or print, that come with a language. You can also design your own. A function is a named block of code that does one job.

Designing a function has two parts. First you define it: you give it a descriptive name, choose its inputs (also called parameters) and write its algorithm. Then you call it: you use its name in the program, with a value for each input.

In block tools, you usually make your own block with a “define” hat. Every time you call the block, its code runs.

Remember: define once, call many times. The input lets one function do slightly different jobs, like flash 2 times or flash 5 times.

Model: design a flash function

Choose a name and an input. Then run the program. Watch how one definition is called twice.

Lesson 2 · Events
CS1.K2

An event is something a program can detect

An event is a detectable action, change or occurrence.

  • Action: someone does something, like pressing a button or clicking a mouse.
  • Change: something in the world changes, like the light level dropping as a cloud passes.
  • Occurrence: something happens, like a timer reaching 10 seconds or a message arriving.

The key word is detectable. The computer must have a way to notice it, through hardware such as a button or a sensor, or through its own software, such as a clock.

Model: can the board detect it?

Tap each happening. Find out whether the board can detect it, and what kind of event it is.

Lesson 3 · Responding to events
CS1.K3

External and internal events

A program can recognize an event and respond to it. In block code, an event hat like “when button A pressed” starts the code under it.

An external event comes from outside the program: a mouse click, a key press, a button press or a sensor reading.

An internal event comes from inside the program or the computer: a timer finishes, or a count is completed.

Between events, the board waits. Code runs only when it is needed.

Model: a tap counter with a timer

Press button A on the board (or use the buttons below). At 5 taps, an internal event shows a smile. Start the 10 second timer for a second internal event.

Lesson 4 · Sensors
CS1.K4

Sensors bring the world into the IPO cycle

A sensor is a device that collects data from the environment, such as light, temperature, moisture, tilt or distance.

Sensors are the input stage of the input–process–output (IPO) cycle. The program processes the reading, often by comparing it to a set value. Then it makes an output, like turning on a pump or a light.

Sensors are used in many applications. Robotics is a big one: a robot uses sensors to find a line, avoid walls or keep its balance. Sensors also run greenhouses, traffic lights and home thermostats.

Remember: a button is an input device you press. A sensor measures something in the environment.

Model: follow one sensor reading through IPO

Choose an application. Move the slider to change what the sensor measures. All set values are examples.

Lesson 5 · Variables
CS1.K5

Variables store information that can change

A variable is a named place in memory that stores a piece of information. Think of a labelled box.

A program can retrieve the value (look in the box) and change it (put something new in the box) at any point while it runs.

In a game, a variable called lives might start at 3. Each time the player is hit, the program changes it by −1. The program retrieves it to show the lives left and to check if the game is over.

Model: watch the lives box

Start the game, then press B to be hit. Each step says whether the variable was changed or retrieved.

Lesson 6 · Names and values
CS1.K6

Give variables good names and the right kind of value

A variable needs a descriptive name that says what it stores, like lapCount or tempOutside. Many languages do not allow spaces in names, so programmers join words.

A variable can be assigned a value in different ways:

  • a number, like set lapCount to 0
  • a string of text, like set playerName to "Amara"
  • the result of a calculation or a sensor reading, like set tempOutside to temperature

The kind of value matters. You can add numbers. You can join strings. Many languages treat the text "5" differently from the number 5.

Model: name check and value check

Part 1: pick a name for a variable that stores the number of laps a skater has finished.

Part 2: choose the kind of value for a and b, then add or join them.

Lesson 7 · Variables at work
CS1.K7

Variables work with loops, conditionals, functions and events

Variables are most useful when they team up with the other parts of a program.

  • Loops: a variable can count how many times the loop has run.
  • Conditionals: a variable can be tested, like if laps = 10.
  • Functions: a variable can be passed in as an input, or changed inside the function.
  • Events: an event can change a variable, like adding 1 each time a button is pressed.

Model: one variable, four teammates

Choose a teammate. Then step through the code and watch laps change.

Lesson 8 · Efficient code
CS1.K8

Efficient code uses functions, variables and events well

Efficient code does its job with fewer wasted steps. It also tends to be shorter, easier to read and easier to fix, so it runs more reliably.

  • Functions stop you from copying the same blocks again and again. Fix the function once and every call is fixed.
  • Variables store a value in one place. Change it once and the whole program uses the new value.
  • Events run code only when something happens, so the program does not spend its own steps checking again and again.

Here is the idea in a skating rink lap counter. A light sensor notices each skater passing the finish line.

Model: three versions of a lap counter

All three versions do the same job. Change the number of laps in the race and compare. Numbers are a simple model.

Teacher notes

  • CS1.K8: “run faster and more reliably” is taught with more precision. Functions and variables mainly make code shorter, clearer and easier to change and fix, which makes it more reliable. Events let the program run code only when something happens instead of checking again and again in a forever loop. In block tools the system still watches for the event behind the scenes, so the saving is in the program’s own steps. Calling a function does not by itself make code run faster.
  • CS1.K3: an internal event such as “a count is completed” is modelled with a “when condition” hat that fires once when the condition becomes true. Some block tools do this with a timer hat or a broadcast message instead. Block names in the lab are generic, not tied to one product.
  • CS1.K6: number and string values are taught. True or false (Boolean) values and lists are mentioned once in the flashcards only. How text that looks like a number is handled varies: some block tools convert “5” to 5 when adding, while Python joins “5” + “5” into “55”.
  • CS1.K4: sensors are described generically (light, temperature, moisture, tilt, distance). A button is taught as an input device, not a sensor. The block heater example (plug in below about −15 °C) is a common Alberta rule of thumb used as an example set value; please check wording.
  • CS1.K1: “functions can be designed” is taught as defining your own function with a name, inputs and an algorithm, and then calling it.
  • Data: all programs, sensor readings, block counts and “checks per minute” figures are made up or simplified for practice and labelled as such.
